## F. Recommended architecture

**Core recommendation: process logs in the browser.** Parse, validate, redact and compute metrics in a framework-free TypeScript module that runs client-side. The file then never leaves the tab, whether the app runs on `localhost` or is later hosted. That satisfies the PDF's local-only constraint without making deployment the decision that blocks everything else.

| Component | Responsibility | Why | Initial release? |
|---|---|---|---|
| `src/features/sessions/` core (pure TS: types, Zod schema, parser, normalizer, dedupe, metrics) | Turn `.md` digests into typed `Session[]` | Every feature downstream depends on it. Unit-testable with the existing `node --test` | **Yes** |
| Client upload UI | File picker / drag-drop, validation, per-file errors | Spec §1 | **Yes** |
| Browser redactor | Re-run redaction on intake, show counts | "Redaction before stored or scored". Logs may come from the older logger or be hand-edited | Yes, before any storage |
| Local store (IndexedDB, behind a repository interface) | Sessions, scores with rubric version, challenges, schedule, constitutions | Trend, spaced review, streaks and version history need persistence. Stays on device. "Delete my data" clears it | Needed by M2 (decision J4) |
| Scoring engine | Deterministic signals first, LLM rubric second; stores `rubricVersion`, reasoning, quote, confidence | Spec §3 | M2 |
| LLM adapter (server route → `src/server/ai/<provider>`, per repo rules) | Rubric reasoning, rewrites, judge, generation | Only path to the "softer" qualities. Requires consent and the J3 decision | M2+, only after J3 |
| Not recommended now | Supabase Auth, Postgres tables for logs, background jobs, cloud storage | Nothing in the PDF needs them under local-only | No |

**Data flow.** File → size/type gate → parse (frontmatter + `[CLAUDE_LOG_ENTRY]` blocks) → normalize (recompute stats from the entries rather than trusting frontmatter) → dedupe by `session_id` → redact → metrics → (later) score → render.

**Privacy boundary.** The raw file and its text stay in the browser. Only redacted, minimal excerpts may cross to the LLM adapter, and only after explicit consent.

**Assumptions.**
- Inputs are `.claude-logs/*.md` digests only, not raw JSONL transcripts.
- English-only UI.
- A single user per browser profile, so no accounts.

**Unresolved:** J1 to J9.

## G. Security and privacy

**Controls verified in the code:**
- Logs are gitignored (`.gitignore` lines 57–58).
- Secret scanner runs in pre-commit and CI.
- The logger's redactor exists and runs before writing.
- Server Pino logger has redaction.
- Env validation fails fast (I saw this happen).
- Security headers are set: HSTS, nosniff, SAMEORIGIN. The CSP only restricts framing, `base-uri` and objects, so it doesn't restrict scripts or connections.
- Analytics, Sentry and PostHog are inert until their env vars are set.

**Nothing related to upload or rendering exists yet, so there are no controls there.**

**Risks and proposed controls.**
1. **Redaction is weak on personal and business data.** The prior review reports it misses emails, home paths with account names, internal hostnames, prose passwords and source code. Run the redactor on intake as well, show what was redacted, and never claim "safe".
2. **Errors and telemetry leaking content.** Parse errors must carry codes, not text. Set Sentry `beforeSend` and breadcrumbs so they drop log content on app routes. No analytics event may carry log text (`docs/rules/analytics.md` already forbids free text).
3. **Safe rendering.** Show log text as plain text through React's escaping. No `dangerouslySetInnerHTML`, no markdown or HTML rendering of logs without a sanitizer. Watch for `javascript:` URLs.
4. **Parsing safety.** Per-file and total size caps as named constants. Cap the entry count. Use linear-time regexes; the logger already had a ReDoS fix. Malformed files are rejected per file with a reason.
5. **No unintended network calls.** Add a test or CSP `connect-src` rule that app pages make no outbound requests during intake.
6. **Retention and deletion.** One "delete my data" action wipes IndexedDB and any caches. Server-side, store nothing in M1–M2.
7. **Dependencies.** Avoid heavy parsers. The format is simple and line-based.
8. **Access.** Local-only means no multi-user access surface. Hosting would reopen this (J1).
